Phase 0 · Unblock deployment

Get the SPA onto a URL, and make the docs reachable

The frontend's share of the deploy work is small — the backend carries most of it. What matters here is that VITE_API_URL is inlined at build time, so the API's public origin has to exist before the production bundle is built.

Gate

F2 cannot be verified until the backend's B1 (CORS from env) and B5 (public API) have landed — see pairings P1 and P2. Everything else in this phase is independent and can be done today.

One API base-URL constant, not two

Blocker

The fallback literal "http://localhost:8181" is duplicated in two files. When the deployed origin changes, one of them will be missed — and the one that gets missed is the RBAC demo page, which is exactly the page a reviewer clicks.

Duplicated at services/api.ts:5 and pages/DemoPage.tsx:9. Export a single constant and import it in both. .env.example already documents the build-time inlining trap correctly.

Effort~30 min
ImpactUnblocks deploy

Phase 1 · Design-system focus

Pick one design system before writing any more CSS

The roadmap card in the architecture brief says "Chakra and Bootstrap and react-bootstrap and two icon sets — a reviewer spots this in ten seconds." The audit found it is sharper than that: this is a custom-CSS app, and almost every UI dependency is removable.

Gate

This phase gates Phase 2. Adding breakpoints or skeleton loaders before the design-system question is settled means writing that work twice — once against Bootstrap's classes and again after they are removed.

Remove the UI dependencies nothing uses

Gate

Three of the four UI packages are effectively dead weight, and the bundle pays for all of them.

react-bootstrap has zero imports anywhere in src/. react-icons is imported only by components/ui/color-mode.tsx, whose own exports (useColorMode, useColorModeValue, ColorModeButton) are never imported by anything. Chakra survives only as a provider that main.tsx:15 forces to dark — so the entire colour-mode machinery is inert.

Effort~3 hrs
ImpactHigh

Decide Bootstrap's fate — commit or extract

Gate

Bootstrap's CSS and its JavaScript bundle are both global imports, and Bootstrap-ish class names appear across 13 files — yet the real design system is the hand-written stylesheet. Either commit to Bootstrap properly or lift those classes into App.css and drop it.

Imports at main.tsx:7 (CSS) and :9 (JS bundle). The actual system is App.css — 1394 lines with its own custom properties (--text-muted) and classes (game-grid, auth-card, stat-card). Must precede F9 and F10.

Phase 2 · Responsive & UX

The gap the docs never admit

The recruiter checklist in the architecture brief has a line for "app works on a phone screen — reviewers open links on mobile". Nothing else in the docs flags responsiveness, and the stylesheet says it is unmet. Once there is a public URL, this becomes the most likely thing to go wrong in front of an actual reviewer.

Add width-based breakpoints

Critical

The stylesheet contains exactly one @media rule, and it is a capability query, not a breakpoint. With a fixed sidebar and a grid layout, the app almost certainly does not survive a 375px viewport — which is what a reviewer opening the link on a phone will see.

App.css — 1394 lines, one @media (hover: none) at :1241, zero width rules. Layout is a fixed sidebar in AppLayout.tsx / AdminLayout.tsx. The viewport meta in index.html is correct, so nothing is masking the problem.

Effort~1 day
ImpactCritical

ErrorBoundary, toasts, and a 5xx path in the interceptor

Do it

The 401 handling is genuinely thoughtful, and it is the only case handled centrally. A 500 or a dropped connection falls through to a page-local string, and a render-time throw takes the whole app to a blank screen.

Phase 3 · Data layer & tests

Most of this phase is gated on backend work — there is no point consuming pagination that does not exist. The two items that are not gated are the test suite and code-splitting, and both are worth doing the moment the design system settles.

Do it

Cross-stack · Recommended Pairings

Nine places where doing one side alone is wasted work

The backend and frontend live in separate repos, which makes it easy to finish a task that cannot be verified — or worse, ship an API shape the client then has to absorb twice. These pairs should be tackled in the same sitting. This section is duplicated verbatim in the backend roadmap.

P1
BackendB1 · CORS origin from envCorsConfig.java:21
FrontendF1 · single API base-URL constantservices/api.ts:5 · DemoPage.tsx:9

Why together: neither is testable on its own. The backend change has no observable effect until a non-localhost origin calls it, and the frontend change has nowhere to point until the backend accepts one. Combined, they are about an hour and they are the deploy unblocker.

P2
BackendB4 + B5 · Docker & Oracle VMcompose · Caddy · TLS
FrontendF2 · Cloudflare Pages deployVITE_API_URL at build time

Why together: the dependency is circular. The SPA bundle needs the API's public origin baked in at build time, and the API's CORS_ALLOWED_ORIGINS needs the Pages domain. Sequence it in one session: bring the API up first, build the SPA against its URL, then set the CORS value to the Pages host and redeploy the API.

P3
BackendB6 · backend briefs → Pagesarchitecture · learning guide · roadmap
FrontendF3 · frontend briefs → Pagesarchitecture · catalog pivot · roadmap

Why together: six documents across two repos, but one story. The existing cross-doc switcher already links between repos using relative filesystem paths — those break the moment the docs are served from two different Pages sites, so the URLs have to be fixed on both sides at once or half the doc set becomes orphaned.

P4
BackendB9 · purchase & library endpointsPurchaseRepository, currently unused
FrontendF14 · real LibraryPageLibraryPage.tsx:15

Why together: the Library page currently calls getAll() and shows every game in the store as though the user owned it. The page is actively misleading, and neither half fixes that alone — endpoints with no consumer prove nothing, and the page cannot be corrected without them.

P5
BackendB10 + B11 · Page<GameResponse>GamesService.searchGames():32
FrontendF13 · consume Page, drop client filtergameService.search → getAll()

Why together: shipping pagination before the DTO forces the frontend through two breaking rewrites — once for the envelope, once when the entity becomes a DTO. Land the final shape and its only consumer in one go.

P6
Backendduplicate-email 400 → 409GlobalExceptionHandler
FrontendF11 · error handling reworkutils/apiError.ts

Why together — and never apart: the brief documents 400 as a deliberate choice "because the frontend keys on 400 for this case", and it does. Changing the status server-side in isolation silently breaks the registration error message with no test failure to catch it. This is the clearest example on the board of a change that is only safe as a pair.

P7
BackendB13 · mvnw verify jobSurefire + Failsafe, H2
Frontendlint + tsc -b + build jobno CI exists in either repo

Why together: a badge that only covers one repo is worse than none — it implies coverage it does not have. Two jobs, authored together, so "green" means the whole stack builds on a clean machine.

P8
BackendB16 · RAWG + tiered cacheCaffeine → shadow rows → RAWG
FrontendF13 / F15 · query layer + degraded banner?search= & page= in the URL

Why together: the design's best detail is the degraded response flag for when RAWG is down and the cache is serving stale rows — and a flag nobody renders is just a field. The pairing also retires the 501 stub button on the admin dashboard, which is currently the most visible unfinished thing in the UI.

P9
BackendB19 · refresh-token rotationhttpOnly cookie + short access token
Frontendsilent renew in the interceptorservices/api.ts:22-34

Why together: today a token that dies mid-session is discovered only when the server rejects a request, and the client responds with a hard page reload. Issuing refresh tokens the client never exchanges changes nothing a user would notice.

Discarded · Quick wins that aren't

Four shortcuts that look cheap and cost more later

All four are genuinely fast, and all four would have to be redone. They are listed so the decision is on the record rather than rediscovered.

Add skeletons or breakpoints before F6

Skip

Both are tempting because they are visible and quick. Both get written against Bootstrap's grid and then rewritten the moment the design-system decision lands. Order matters more than speed here.

Install a toast library now

Skip

Adds a fifth UI dependency to a project whose main frontend problem is that it already has too many — and the design-system decision may supply a toast primitive for free.

Wire up the colour-mode toggle

Skip

Looks like finishing something half-built. It is not: main.tsx:15 forces dark deliberately, and the app's entire visual identity is a dark theme. Making the toggle work means authoring a light theme for 1394 lines of CSS — that is net-new scope, not a fix.

Paginate client-side over getAll()

Skip

Gives the appearance of pagination while still downloading the whole catalogue, and cements a component API that server-side paging will invalidate. Wait for B10.

Also deliberately out of scope, per the architecture briefs: Kubernetes · Redis · microservices · Kafka / event sourcing / CQRS · GraphQL · Terraform. One bounded context does not need any of them, and reaching for them reads as résumé-driven complexity.
