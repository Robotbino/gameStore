Full-Stack Architecture Brief

Game Store — React + Spring Boot commerce platform

A stateless, JWT-secured e-commerce stack: a TypeScript React SPA talking to a Spring Boot REST API over role-based access control, persisted in MySQL via JPA/Hibernate. This document walks the system top-to-bottom — components, requests, state, and failures — with interactive layers, sequence diagrams, and traceable code paths.

§ 2 · Interactive Layer Explorer

What lives where

Layer 1 — React SPA (browser)

Ships from Vite on port 5173. React renders pages behind two guards (ProtectedRoute, AdminRoute). All HTTP goes through a single axios instance so the Bearer token is attached in exactly one place. Auth state lives in React context, backed by localStorage for reload survival.

Layer 2 — Spring Boot API

Every request hits JWTAuthenticationFilter before touching a controller. On a valid token the filter builds an Authentication and drops it in the SecurityContext; on a missing/invalid one it either lets the request through (if the path is public) or the chain returns 401. Controllers stay thin — parse in, delegate to a service, return a DTO. GlobalExceptionHandler converts thrown exceptions into the JSON error envelope the frontend expects.

Layer 3 — MySQL via JPA / Hibernate

Three tables, mapped as JPA entities. Repositories extend JpaRepository, giving us CRUD for free and letting us declare derived queries by method name (findByTitleContainingIgnoreCase is one line of interface). Hibernate manages the schema, runs the SQL, and keeps entities inside a transaction so relationship traversals work inside a service call.

Step 3 · HTTP goes out
axios → /api/v2/auth/authenticate

The request interceptor would attach a Bearer token if one existed — for login there isn't one yet, so this call is public.

Step 4 · Backend authenticates
AuthController → BCrypt → JwtService

Spring Security's AuthenticationManager re-hashes the input and compares against the stored bcrypt digest. If it matches, JwtService.generateToken() signs a JWT with sub=email, role, and exp.

Step 5 · Token comes back
applyToken() decodes and stores

The context decodes the JWT client-side purely to read role and expiry — no signature check on the client; the server is the only trust anchor.

Step 1 · Server rejects
401 from JWT filter

The filter sees the exp claim is in the past and refuses to authenticate the request. The response leaves the API as 401 before it ever reaches a controller.

Step 2 · Response interceptor
api.ts filters login vs everything else

A 401 from /auth/** means "bad credentials"; a 401 anywhere else means "session died". The interceptor treats them differently — it clears storage only for the second case, so the login page can still surface "invalid password" without triggering a logout redirect.

if (error.response?.status === 401) {
  const url = error.config?.url ?? "";
  if (!url.includes("/auth/")) {
    localStorage.removeItem("token");
    window.location.href = "/login";
  }
}
services/api.ts:22
Step 3 · Hard reload resets everything
window.location.href, not navigate()

A full reload guarantees every in-memory cache is wiped, not just React state — no stale queries can fire against the dead session.

Step 4 · Rehydrate finds nothing
AuthContext startup effect

On the fresh page, the mount effect reads localStorage.getItem("token"), finds null, and settles into the logged-out state without noise.

§ 4 · Client Auth State Machine

Every state AuthContext can be in

Auth is not just "logged in / out". The context has a startup phase where it doesn't yet know, and every transition is triggered by exactly one event. The router waits for Loading to end before deciding where to send anyone. 

stateDiagram-v2
  [*] --> Loading: app mounts
  Loading --> AnonymousUser: no token in storage
  Loading --> AuthenticatedUser: token valid
  Loading --> AnonymousUser: token expired / malformed

  AnonymousUser --> AuthenticatedUser: login()/register() success
  AnonymousUser --> AnonymousUser: login() rejected (401)

  AuthenticatedUser --> AdminUser: role claim = ADMIN
  AuthenticatedUser --> AnonymousUser: logout()
  AuthenticatedUser --> AnonymousUser: interceptor 401 (session died)

  AdminUser --> AnonymousUser: logout()
  AdminUser --> AnonymousUser: interceptor 401

Diagram 3 · isLoading is a distinct state, not a boolean flavor of "logged out" — that's why ProtectedRoute shows a spinner instead of bouncing to /login on first paint.

Why the loading state matters
Without it, a page refresh on /library would run the redirect before the mount effect finished rehydrating the token, and the user would be thrown to /login despite having a perfectly valid session. The gate literally exists to close that window.
Why decode the JWT on the client at all?
Only to read display data (sub, role) and drop obviously-dead tokens on the floor. Access decisions are re-checked on the server for every call — the client's decoding is UX, not security.

§ 7 · Failure Modes

What can go wrong, and who catches it

A short catalog of the error paths, mapped to the code that handles each one. The extended state (§ 9) upgrades several of these from "silent console error" to "toast the user sees".

401 · Unauthorized

Bad credentials on login

Path matches /auth/**, so the response interceptor does not log the user out — LoginPage shows the returned message inline.

401 · Session expired

Token dies mid-session

Any non-/auth/ 401 clears localStorage and hard-redirects to /login. See Flow D.

403 · Forbidden

USER hits an ADMIN endpoint

SecurityFilterChain rejects before the controller runs. UI usually hides these links; the check on the server is the real one.

404 · Not found

Client-side unknown route

Catch-all route renders NotFoundPage instead of bouncing to home — surfaces the wrong URL to the user.

5xx · Backend error

Uncaught exception in a service

Bubbles into GlobalExceptionHandler, which returns a consistent JSON error envelope. The extended state wires this to a toast (§ 9 feature 03).

— · Network dropped

Offline / server down

axios rejects with no response. Callers catch and set a page-local error message; the interceptor leaves the token alone.

§ 8 · The Increment

Three low-effort, high-signal features

Each plugs into scaffolding that already exists — axios interceptors, a GlobalExceptionHandler, the shared GameGrid, and existing entity fields — so nothing here touches the schema, the auth model, or the timeline.

Skeleton loaders

Swap the plain "Loading games…" text for shimmer cards that mirror GameCard's layout while isLoading is true. Kills layout shift and signals perceived-performance maturity on first paint.

Server-side search & sort

03 / RESILIENCE

Global error handling

Kubernetes

Skip

One container per service on one VM. Compose is the correct tool; k8s here is résumé-driven complexity that a good reviewer reads as a lack of judgment, not a surplus of skill.

Redis

Skip

Caffeine (in-process) plus a MySQL shadow table already cover the cache need at this scale. A second datastore to run, secure and back up buys nothing here.

Microservices

Skip

This is one bounded context. A well-layered monolith is the right architecture — splitting it would add network calls and deploy pain to solve a problem the app doesn't have.

Kafka / event sourcing / CQRS

Skip

No async workload, no audit-log requirement, no read/write asymmetry that a broker or an event store would relieve. These solve problems a store this size never encounters.

GraphQL

Skip

The REST surface is small, stable and well-documented. GraphQL's flexibility is a cost with no matching benefit until clients need to shape wildly varied queries.

Terraform / IaC

Skip

One VM provisioned once. A documented compose.yml and a short runbook are the right level of "infrastructure as code" for a single-node portfolio deploy.
