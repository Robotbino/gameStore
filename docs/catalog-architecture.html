Architecture Brief · Catalog Pivot

External Catalog — owning commerce over data you don’t own

The product catalog moves to RAWG’s live API. Auth, carts, orders and pricing stay in MySQL. That split raises one hard question — how do you foreign-key an order line to a product that lives on someone else’s server? This is the answer.

The third tier is the whole trick: RAWG and MySQL sit side by side, and MySQL keeps a lazily-populated shadow row for every game anyone has ever looked at.

The Core Problem

You cannot foreign-key across a network boundary

An order_items row needs to point at a product. If the product only exists as RAWG id 3328, the database can enforce nothing — and purchase history is one upstream edit away from lying to the customer.

Naive passthrough

Rejected

Store the remote id as a loose column and resolve it at render time. Nothing is enforced, every cart page becomes N remote calls, and joins move into application loops.

order_items.idBIGINT PK
rawg_id3328 — no FK
titlefetched live → may change
pricerecomputed → receipt drifts

Integrity: none. History: mutable.

Lazy shadow table + snapshot

Chosen

A local games row is upserted the first time a title appears in any search result. The FK is real and database-enforced; the snapshot preserves what was actually sold.

order_items.idBIGINT PK
game_id→ games.id · FK ✓
title_snapshotfrozen at checkout
unit_pricefrozen at checkout

FK for integrity · snapshot for truth.

Why both, and not one or the other. The foreign key keeps joins and referential integrity honest — “how many users own this game?” stays a single query. The snapshot keeps history immutable, because a shadow row is a cache, and caches are allowed to change: RAWG retitles games, the price formula will eventually be retuned, titles get delisted. Join live to games and a customer’s March receipt silently rewrites itself.

Identity

Composite keys, and nothing is ever deleted

Two constraints on the games table carry most of the design’s weight.

UNIQUE (source, external_id)

Never external_id alone — RAWG id 3498 and IGDB id 3498 are different games. Hand-entered rows carry source='LOCAL' with a null external id, and because MySQL treats nulls as distinct in a unique index, unlimited local rows coexist. This single constraint is what makes “add IGDB later” real rather than aspirational.

status — flag, never DELETE

Deleting a shadow row would break the FK from every historical order containing it. When a refresh 404s, the row is marked UNAVAILABLE instead: libraries still render it, browse and search exclude it, and add-to-cart rejects it with a real message.

Read Path

Three tiers, cheapest first

RAWG’s free tier allows 20 000 requests a month — roughly 660 a day. A single afternoon of hot-reloading a search box would eat 500 of them. The ordering below is what makes that a non-issue, and it is also what turns a RAWG outage into a banner instead of an error page.

Tier 1 · in-process

Caffeine

Search 10 min, detail 24 h, genres 7 days. Annotated on the provider, not the controller, so the internal materialization path is protected too.

Hit → ~0 ms, 0 quota
Tier 2 · durable

MySQL shadow row

Survives restarts, which is what actually saves you in development. Serves reads while cached_at is under 14 days old — and serves everything when RAWG is down.

Hit → one local query, 0 quota
Tier 3 · remote

RAWG API

Reached only on a genuine miss, with explicit 2 s connect and 4 s read timeouts — RestClient’s default factory has no read timeout at all.

Miss → 1 call, then batch-upserted

Quota consumption scales with distinct games ever touched — a few thousand — not with RAWG’s ~880 000 title catalog. A full nightly ETL would need ~22 000 requests per pass, exceeding the entire monthly allowance in a single run.

The Flow

Search to receipt, end to end

Step 04 is the pivot the whole architecture turns on — the moment remote data acquires a local primary key, and every downstream feature gets to be ordinary.

Guest searches “witcher”

React issues GET /api/catalog/games?q=witcher&page=1. No token required — the catalog is permitAll, so the store is browsable before signup.

Cache ladder is walked

Caffeine miss, then no fresh shadow rows, so RawgCatalogProvider is called. The response maps into provider-neutral CatalogGame records — RAWG’s own DTOs never escape their package.

Price is synthesized once

RAWG ships no prices. A deterministic formula derives one from metacritic score and release age, then it is persisted and never recomputed — otherwise retuning the formula would silently reprice everything sitting in customers’ carts.

Batch upsert — remote data becomes local

All 40 results are matched against MySQL in one query keyed on (source, external_id), then inserted or refreshed via saveAll. Every result now carries a local Long id — so routes, cart calls and foreign keys need no provider-aware URL scheme at all.

Add to cart

POST /api/cart/items with a local id. UNIQUE(cart_id, game_id) makes it idempotent, and there is no quantity column — you cannot buy two copies of a digital licence.

Checkout, inside one transaction

Reject empty carts, non-ACTIVE titles, and already-owned games; then write orders and order_items with title, image and price snapshotted, clear the cart, and award loyalty points.

Library renders from owned rows

GET /api/library runs a single projection over order_items — not a walk over orders — so it stays one query regardless of purchase count.

When RAWG is unreachable. The provider returns a failure, the service falls back to tier 2, and the response carries a degraded flag — a “showing cached results” banner rather than a 500. After several consecutive failures a short circuit-breaker window stops calling out entirely for 60 seconds. A store that degrades is a better store than one that errors.

Game data provided by RAWG. Metadata is cached locally for performance; images are hotlinked, never re-hosted.
